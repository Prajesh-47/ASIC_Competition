## 2. The FPGA build

### What failed, and why

`.github/workflows/fpga.yaml` runs `TinyTapeout/tt-gds-action/fpga/ice40up5k@ttihp27a`. That action
([action.yml](https://github.com/TinyTapeout/tt-gds-action/blob/ttihp27a/fpga/ice40up5k/action.yml)) checks out
`tt-support-tools` and runs `python tt/tt_fpga.py harden`. That script
([tt_fpga.py](https://github.com/TinyTapeout/tt-support-tools/blob/main/tt_fpga.py)) wraps the project in
`fpga/tt_fpga_top.v`, then runs:

```
yosys -DSYNTH -p 'read_verilog -sv _tt_fpga_top.v <info.yaml source_files>; synth_ice40 -top tt_fpga_top -json ...'
nextpnr-ice40 --up5k --package sg48 --freq 12 --pcf tt_fpga_fabricfoxv2.pcf ...
```

The source list is `info.yaml`'s, so it includes `src/RM_IHPSG13_1P_512x16_c2_bm_bist.v`, which was an empty
blackbox. iCE40 has no such cell, so the build failed with `cell type 'RM_IHPSG13_1P_512x16_c2_bm_bist' is
unsupported`. The action has no inputs for defines or for a separate source list. The `-DSYNTH` it always
passes is the only thing it gives us to tell the two builds apart.

### The fix

`src/RM_IHPSG13_1P_512x16_c2_bm_bist.v` now has a behavioural body inside `` `ifdef SYNTH `` and
`` `ifndef __librelane__ ``. It's an inferred 512x16 RAM: a write when `A_MEN && A_WEN` (bit mask honoured),
otherwise a read into an output register when `A_MEN && A_REN`. That matches the PDK model in
`test/models/` except for BIST and write-through. SPLICE never asserts `A_WEN` and `A_REN` together: for
`prog_sram`, `host_prog` needs `!running`, and for `cap_sram`, `host_cap` needs `!cap_we`.

LibreLane never defines `SYNTH`. Its synthesis script adds `PDK_*`, `SCL_*`, `__librelane__` and `__pnr__` to
`VERILOG_DEFINES` ([synthesize.py](https://github.com/librelane/librelane/blob/main/librelane/scripts/pyosys/synthesize.py)),
and `src/config.json` sets no defines. The `__librelane__` guard covers us if a future version ever adds
`SYNTH`. Simulation defines `SPLICE_SRAM_MODELS` and doesn't see this file's module at all, as before.

### How it was checked

| Check | Result |
|---|---|
| ASIC-style synthesis before and after, two ways (yosys 0.33): `gl_yosys.sh`'s recipe with the macro read as `-lib`, and LibreLane's way with the macro file among the sources and `-D__librelane__ -D__pnr__ -DPDK_ihp_sg13cmos5l` | **15,258 cells and 2 macro instances both times. The written netlists are byte-identical** (same MD5 before and after, `a796b45a…`) |
| RTL suite, `cd test && make`, then `python -m cocotb_tools.check_results results.xml` | **77/77 pass**, `check_results` exit 0 (7 min 15 s) |
| FPGA synthesis, the exact `tt_fpga.py` command (yosys 0.33, `synth_ice40`) | Synthesises. The macros become **4 `SB_RAM40_4K`** (2 per macro, of 30) |

### Does it fit an iCE40UP5K? **No.**

| Resource | SPLICE (4 contexts) | UP5K has | Use |
|---|---:|---:|---:|
| LUT4 | **6,222** | 5,280 | **118%** |
| Flip-flops | 2,174 | 5,280 | 41% |
| `SB_CARRY` | 520 | (in the same logic cells) | |
| Block RAM (4 Kbit) | 4 | 30 | 13% |

Synthesis estimate from yosys 0.33. The CI's oss-cad-suite is newer and nextpnr packs differently, but
not by 18%. By module (`-noflatten`), the engine is 4,856 of the LUTs. Its per-context state is muxed out of
flip-flops, and iCE40 has no distributed RAM to hold it.

**Alternative, not built:** the engine is already `splice_engine #(parameter NCTX = 4)`. Setting `NCTX` with
`chparam` in the FPGA synthesis alone gives:

| `NCTX` | LUT4 | Use of 5,280 |
|---:|---:|---:|
| 4 | 6,222 | 118% |
| 2 | 4,789 | 91%, likely too full to place and route at the demo board's clock |
| 1 | 3,932 | 74% |

An FPGA-only `NCTX` would need an RTL change: the top level wires `halted` and the context-count register
as 4 contexts, and `NCTX` below 4 has never been tested. That's against the freeze, and an FPGA build that
isn't the chip proves less. My recommendation is to **not** do it. Instead, either state plainly that the
design synthesises but doesn't fit the UP5K and drop the badge, or, if hardware evidence is wanted, use a
larger FPGA with the full design (an ECP5 or Gowin board through yosys and nextpnr, outside the Tiny Tapeout
action). That's the author's call, since it means buying a board.

### Workflow run

One push and one dispatch of `fpga.yaml` on this branch. Its result is in the commit after this one, or
in the hand-off. The expected result is that synthesis passes and nextpnr fails on LUT count.

## 3. How other entries present themselves

Repositories found with `gh search repos` ("protocol emulator", "jane street asic" and similar), 22 READMEs
read on 2026-11-28. Many are the unchanged Tiny Tapeout template. The ones with real content:

| Entry | How it leads | What it presents that SPLICE doesn't |
|---|---|---|
| [Escapement](https://github.com/parthDOOM/escapement) | A one-line claim in bold ("No pin edge is ever late … Proved"), then the protocol list, then a mermaid block diagram | A [site](https://parthdoom.github.io/escapement/) with "the firmware running in your browser" under Pyodide. RTL on a Tang Primer 25K run from a Pico W (89 of 90 programs). A **sealed held-out round** of 8 protocols, with the drawn list hashed before any was written. `make quickstart`. Claims 10BASE-T |
| [MarcosAsh/protocol-emulator](https://github.com/MarcosAsh/protocol-emulator) (Hardcaml) | A one-paragraph claim, a "firmware to silicon" SVG, and a fact table where every row names its source file or gds run | A [playground](https://marcosash.github.io/protocol-emulator/playground/) ("No install … runs the kernel in your browser"). RTL on an Icepi Zero (ECP5) with 42 recorded witnesses. Pages for getting started, "Compared with PIO and PRU" and "How AI was used". Claims USB full speed and 10BASE-T |
| [Tempo](https://github.com/satyaammu93/jane-street-asic-2026) | Links to an [interactive walkthrough](https://satyaammu93.github.io/jane-street-asic-2026/tempo.html) on the first lines | A browser walkthrough of UART and SPI execution. A table of what was and wasn't done, with "FPGA … not performed" stated plainly |
| [Tarang](https://github.com/prasadp4009/tt_um_pemu) | Badges, 11 images, a long README | A Zybo FPGA port with logs and bitstreams in the repo. An interactive GDS explorer |
| [protocol-emulator-asic](https://github.com/mrnathanhumphrey-droid/protocol-emulator-asic) | Template badges, then a table-driven design | v1 on an Artix-7 with recorded "witnesses", and FPGA-measured I2C and UART tolerances next to the simulated ones |
| [Rishadd/protocol_emulator](https://github.com/Rishadd/protocol_emulator) | A status table of protocols, then "not done" | FPGA bring-up scripts with `--sim` and board modes |
| [Weft](https://github.com/fuzzylogique/weft) | A results table that includes "FPGA build: not attempted" | States what it hasn't done in the results table |
| [dhruvauppaluri](https://github.com/dhruvauppaluri/Dhruva-Uppaluri-JaneStreetASIC) | "What it can do that a fixed-function chip can't" | A learn-and-impersonate demo: sniff I2C, learn the device, impersonate it |

**What we lack, by how many have it:**

- **Hardware evidence:** at least 5 of the entries above show RTL on an FPGA board. SPLICE has none, and its
  FPGA badge is red.
- **A browser demo:** 3 (Escapement, MarcosAsh, Tempo). SPLICE has `python -m splice.run`, which needs a
  clone.
- **A one-sentence claim at the top:** most strong entries open with one. SPLICE's opening ("A protocol
  emulator you reprogram in firmware … can also sit inline …") is good, but it comes after a mode table.
- **Facts with sources:** MarcosAsh's table gives a file or a gds run on every row. SPLICE's numbers have
  sources in `ai-log.md`, but not on the README.
- **A dedicated "How AI was used" page,** which the FAQ asks for in the write-up. SPLICE's `ai-log.md` is
  thorough but is a log, not a write-up.

**What is still SPLICE's alone:** none of the 22 READMEs describes inline alteration of live traffic, an
open-drain bridge with a proof, or MITM, interposing or fault injection (a keyword search for those terms,
plus "pass-through", found nothing relevant). The earlier scan's conclusion stands. "Sealed blind trial"
is no longer unique (Escapement has a hashed held-out round), so the write-up should lead with interposing
and trial 3's results, not with the sealing.

This is a README scan, so it can't rule out features that aren't written down.

## 5. Firmware capabilities not yet shown

| # | Capability | What SPLICE already has for it | Status |
|---:|---|---|---|
| 1 | **10 Mbit Ethernet transmit** (stretch goal) | `CODE man`, link FIFOs, `CRCW` for CRC-32 in software or a table. **Measured here** (`lab/explore/man10.py`, `fw/man_tx_probe.s`): half-bits of 5, 4 and 3 cycles are exact over six back-to-back words; 2 cycles is 1 cycle late at 2 of 5 word boundaries in a naive loop | At 60 MHz (HB 3) the coding is exact on the model. Needs a preamble, SFD, CRC-32, the end of frame and link pulses. Receive is harder (half-bits of 3 cycles, with sync) and wasn't tried. At 50 MHz it can't be done (2.5 cycles) |
| 2 | **A bus fuzzer:** inline faults at a `RAND`-chosen or swept bit, with the device's reaction captured | `MODE`, `RAND`, the capture unit, and the host link for the log | Nobody's README describes it. Built from what the I2C NACK and UART flip demos already use |
| 3 | **SPI flash read patching inline:** rewrite MISO bytes at chosen addresses as the controller reads | Fast pass-through, `MODE` on an exact cycle, `CMPK` for the address | Synacktiv concluded that a microcontroller is poorly suited to patching SPI MISO on the fly, and pointed to an FPGA ([Synacktiv](https://synacktiv.com/publications/car-hijacking-swapping-a-single-bit)). SPLICE doing it in firmware is a strong story. Depends on SPI clock against the 1/n rate |
| 4 | **CAN error injection on a chosen ID and bit,** inline | CAN receive with sync, `CMPK`, `MODE` | The scout's match-rule idea, done in firmware with two contexts |
| 5 | **A live timing checker** on a passed-through bus: I2C setup and hold, or UART bit width, flagged on `TRIG_OUT` | `TCAP`, `CMPUI`, edge ticks | Escapement does this in hardware (a "bus timing monitor"). SPLICE would do it in firmware, on a bus it's also forwarding |
| 6 | **Protocol identification:** histogram edge intervals on an unknown line and guess UART baud, Manchester or PWM | `TCAP` | Lower novelty: two entrants already learn baud rates or devices |

## 6. Re-hardening after the deadline

The competition page says: "After the deadline, we'll work with winners on small **non-functional** fixes,
like re-hardening for a newer flow." The FAQ adds that Tiny Tapeout isn't planning changes to 8x4 that would
need re-hardening ([competition page](https://blog.janestreet.com/protocol-emulator-asic-competition/)).

**So no silicon features can be added after the deadline.** What the window can be used for:

| Fix | Worth it? |
|---|---|
| The last slew violation (`cap_sram/A_WEN`, 0.04 ns) and the four fanout violations, against a fixed placement | Yes, already deferred to signoff |
| Closing timing at **60 MHz** (16.67 ns) instead of 50 | Yes, if it closes. It makes 10BASE-T's half-bit a whole 3 cycles. Today's 1.68 ns slack at 20 ns leaves about −1.6 ns at 16.67 ns in the slow corner. Same RTL, so it's arguably non-functional, **but run it as a gds experiment before the deadline** rather than counting on it |
| A newer LibreLane, or updated SRAM views from IHP | If the organisers ask |
| Re-enabling the disabled flow checks (Magic DRC, illegal overlaps), if a newer flow handles the macros | Yes, it strengthens the signoff story |

**Silicon features to settle before 2027-01-18,** since later is too late: the flop boot store (the
roadmap's top risk, still awaiting a choice), and nothing else that trial 2 showed is needed. The freeze on
2026-11-29 is self-imposed. The real cut-off for silicon is the deadline, but every feature still costs
timing margin and write-up time.
